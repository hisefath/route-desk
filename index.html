System design

The model proposes. The supervisor commits.

One operator, one sandbox merchant, one process. The desk watches approval rate, and the number it is responsible for is recovered authorizations: attempts on a slice times the gap between the current provider and the best one it is allowed to move to.

Formula

recovered = attempts × (best rate − current rate) only where the other provider's decline mix can take the traffic only after a person approves the move
  • Recovered authorizations are the star. Approval rate, decline mix, and minutes the signal stays red are how you get there.
  • Run count, token cost, and leases are desk health. They do not move the star.
  • A restart must still be waiting on the same approval. The wait is a row, not a lock in memory.
  • The same route change applied twice, or retried after a crash, writes one sandbox row.

High-level design

Five containers, one door to the book.

The sandbox is a port inside the orchestrator. A network hop would not make the approval check stronger. The tool router is the door.

Operator UIConfig, the proposal, the traces. On failure the run row is unchanged.
OrchestratorAPI, scheduler, supervisor, two workers, tool router, sandbox port.
SQLiteEvery durable noun. If it is down, the API returns 503 and approves nothing.
Model providerCompletions and token counts. Timeout, backoff, then the step fails. Eval uses a scripted client on the same port.
TelegramInbound only. A bad signature is a 401 and no run. The body is data, not an instruction.
Sandbox portRates, decline reasons, and one routing write. The write commits with the effect row.

When a line fails

  • Scheduler to supervisor: one claim update. The loser finds the lease held.
  • Worker to model: bounded retries, then the run ends failed.
  • Router to sandbox: crash after commit is recovered by reading the row, not by calling the tool again.
  • Chat down: the UI still approves, because both resolve the same approval row.

Low-level design

Status is a column. The model never writes it.

Workers write the state document through a version check. The supervisor is the only writer of runs.status. Approve is compare-and-set. Apply is one transaction.

queued→running→waiting_approval→running→succeeded

Rejected, cancelled, and timed_out are the other terminals. A passed deadline is applied when the scheduler next claims the row.

Claim

UPDATE runs SET status = running, lease_until = now + 30s WHERE id = ? AND status IN (queued, waiting_approval) AND (lease_until IS NULL OR lease_until < now)

Approve

UPDATE approvals SET status = 'approved', decided_at = ? WHERE id = ? AND status = 'pending' -- zero rows: the other click won

Apply

BEGIN approval must be approved for this step INSERT routing_changes (idempotency_key PRIMARY KEY) ON CONFLICT read the existing row store effect_id, mark the step succeeded COMMIT

State write

UPDATE runs SET state_json = ?, state_version = state_version + 1 WHERE id = ? AND state_version = ? -- zero rows: reload, do not call the model again
